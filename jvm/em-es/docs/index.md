# Эмиттанс и энергетический разброс

## Аннотация

Модуль предназначен для оценки эмиттанса и энергетического разброса пучка заряженных частиц. По своей сути модуль выполняет численную минимизацию заданной физической модели с использованием полученных измерений размера пучка в качестве наблюдений. Алгоритм разработан как для обработки данных в реальном времени, так и для воспроизведения эксперимента.

## Физическое обоснование

### Описание физической задачи

Моделируется зависимость эмиттанса и энергетического разброса пучка заряженных частиц от его тока. Уравнения, описывающие зависимость размеров пучка от параметров (см. [1]):

$$
\sigma_x^2 = \beta_x\varepsilon + (D_x\sigma_e)^2
$$

$$
\sigma_z^2 = \beta_z\varepsilon + (D_z\sigma_e)^2
$$

где

- $\sigma_{x, z}$ — размер пучка;
- $\beta_{x, z}$ — бета-функция;
- $D_{x, z}$ — дисперсия орбиты пучка;
- $\sigma_e$ — энергетический разброс;
- $\varepsilon$ — эмиттанс.

Допущения:

- Размер пучка в накопительном кольце определяется поперечным распределением частиц, которое является гауссовским при низких токах (микроамперы). Таким образом, под размером пучка подразумевается ширина гауссовского распределения.
- Измерения размера пучка не синхронизированы по времени и требуют дополнительной предварительной обработки.
- Измерения размера пучка имеют определённую техническую точность, определяемую:
  1. Фокусировкой изображения в плоскости CCD-сенсора
  2. Размером зерна CCD-сенсора
  3. Алгоритмом аппроксимации изображения пучка двумерной гауссовой функцией
  4. Переэкспонированием CCD-сенсора и наличием бликов

С учётом последнего пункта, для практических целей приведённые выше выражения могут быть переписаны следующим образом:

$$
\sigma_x^2 - \beta_x\varepsilon + (D_x\sigma_e)^2 \ge 0
$$

$$
\sigma_z^2 - \beta_z\varepsilon + (D_z\sigma_e)^2 \ge 0
$$

### Вычислительный подход

Предположения об ошибках измерений, описанные выше, опускаются и считаются разрешёнными на предварительных этапах посредством фильтрации или иных методов оценки стохастических параметров.

При сохранении знака равенства выполняется численная минимизация неявно заданной вектор-функции для параметров, представляющих интерес (эмиттанс и энергетический разброс).

## Обзор модуля

### Область применения

Данный модуль выполняет две основные задачи:

1. Временную синхронизацию событий измерения размера пучка и тока
2. Оценку значений эмиттанса и энергетического разброса

Как отмечалось ранее, модуль не отвечает за фильтрацию измерений. Влияние погрешностей измерений на полученный результат не вычисляется.

### Архитектура

1. Основные подсистемы
   1. Математическая библиотека — программная реализация основного метода (Гаусс-Ньютон) и вспомогательных математических процедур.
   2. Библиотека ввода-вывода — набор расширений для основной вычислительной системы (Apache Flink), предназначенных для работы с потоками измерений и параметров (агрегация, объединение и т. д.).
   3. Конфигурация — подсистема доступа к конфигурационным файлам.

## Установка и настройка

### Системные требования

1. Требования к платформе зависят от способа запуска модуля. Для изолированного режима единственным требованием
   является Docker Engine. При запуске в качестве задания в кластере Apache Flink дополнительные требования не
   предъявляются.
2. Вся коммуникация осуществляется через Apache Kafka (как для режима реального времени, так и для режима воспроизведения
   эксперимента).
3. Для достижения максимального соотношения параллельного выполнения в кластерном режиме количество свободных слотов должно быть не менее
   количества используемых входных каналов.

### Установка и запуск

#### Система сборки

Проект является модулем Gradle. Все команды выполняются из корневого каталога. Основные задачи перечислены ниже.

Команда для генерации Java-моделей из Avro-схем (выполняется однократно при изменении схемы; результат сохраняется в репозитории):

```bash
./gradlew :core:beam.em-es:avro
```

Команда для сборки FatJar (требуется для работы в кластерном режиме):

```bash
./gradlew :core:beam.em-es:shadowJar
```

Команда для сборки Docker-образа (требуется для работы в изолированном режиме):

```bash
./gradlew :core:beam.em-es:image
```

### Верификация

Модуль можно запустить сразу после установки. Стандартная конфигурация предполагает работу в реальном времени с 4 камерами: 1M1L (x, z), 1M2L (x, z), 2M1L (x, z) и 2M2L (x, z). После запуска модуль считывает конфигурацию и ожидает появления данных в соответствующих каналах. В случае ошибки выполнение будет прервано, и на экране терминала появится соответствующее сообщение с дополнительной информацией.

## Руководство пользователя

Алгоритм предполагает, что время события будет возрастать (см. корневую документацию). Это означает, в частности, что изменение режима работы должно сопровождаться перезапуском модуля (или параллельным запуском его второй копии).

### Режим работы в реальном времени

По умолчанию модуль работает в реальном времени. Это означает, что после запуска считывание данных из входных каналов начинается с последнего события и никогда не завершается.

1. Данные подаются во входные каналы по мере их создания.
2. Система настроена без поля `replay`.
3. Результат доступен по завершении обработки каждого окна.

### Режим воспроизведения эксперимента

В режиме воспроизведения эксперимента данные с камер за весь выбранный период записываются во
временные каналы (см. документацию по инфраструктуре). После запуска модуль начинает считывать
каналы с указанного смещения, равного размерности эксперимента. После обработки всех данных модуль завершает работу.

1. Данные подаются во входные каналы в полном объёме.
2. Система настроена с полем `replay`, установленным в значение, равное номеру эксперимента
   (это значение будет использоваться для идентификации временных каналов, из которых следует читать).
3. Результат доступен по завершении обработки каждого окна (это означает, что, как и в режиме реального времени, данные
   обрабатываются последовательно).

### Интерпретация результатов

Выходные данные модуля доставляются в два канала:

1. `v2k.beam.em` — содержит значения тока пучка и эмиттанса.
2. `v2k.beam.es` — содержит значения тока пучка и энергетического разброса.

Схемы выходных данных расположены в каталоге `schema` и могут использоваться другими модулями для интерпретации данных.

#### Визуализация

Для визуализации результатов предоставляется dashboard Grafana, содержащий две визуализации:

1. Зависимость эмиттанса пучка от тока.
2. Зависимость энергетического разброса пучка от тока.

## Ограничения, точность и валидация

### Числовые характеристики

1. Источники погрешности
   - Линеаризация исходной функции до первой производной.
   - Погрешность решения системы линейных алгебраических уравнений внутри алгоритма (зависит от
     метода).
   - Машинная точность и ошибки округления.

2. Сходимость

   В чистом виде (без дополнительных модификаций) алгоритм может сходиться к нескольким локальным минимумам. Предусмотрен защитный механизм от вырождения промежуточных величин в случае множественных решений.

   Для ограничения рабочего диапазона алгоритма может быть введена дополнительная проверка _физичности_ параметров. Например, область определения параметров может быть ограничена положительными значениями.

   Ограничение области определения параметров должно выполняться с крайней осторожностью. В некоторых случаях это может препятствовать сходимости к границе области определения. Если функция ограничения является нелинейной (например, экспоненциальной), валидация параметров может вносить дополнительную машинную погрешность.

## Документация

### Реализация ключевых алгоритмов

#### Минимизация

С математической точки зрения задача состоит в минимизации неявно заданной векторной функции:

$$
F(x) = 0,\ x = (\varepsilon,\ \sigma_e)^T
$$

В форме функционала наименьших квадратов задача формулируется следующим образом:

$$
\Phi = \sum_{k=1}^{n}(\omega_kF_k(x))^2 \rightarrow min_{x}
$$

где $n$ — количество точек наблюдения, $F_k$ — неявное уравнение для $k$-й точки
(ось камеры), а $\omega_k$ — вес $k$-й точки. Веса устанавливаются пользователем.

Продифференцируем функционал по параметрам и приравняем к нулю:

$$
2\sum_{k}\omega_k^2F_k(x)\frac{\partial F_k(x)}{\partial x_j} = 0,\ j=1,2
$$

Разложим $F_k(x)$ в ряд Тейлора до первой производной:

$$
F_k(x) \approx F_k(x - \Delta x) +
    \sum_{p=1}^2\Delta x_p\frac{\partial F_k(x - \Delta x)}{\partial x_p}
$$

Подставляя в исходное уравнение, получаем линеаризованную систему:

$$
A\Delta x = b
$$

где

$$
A_{ij} = \sum_{k}\omega_k^2\frac{\partial F_k(x^n)}{\partial x_i}
    \frac{\partial F_k(x^n)}{\partial x_j}
$$

$$
b_{i} = -\sum_{k}\omega_k^2 F(x^n) \frac{\partial F_k(x^n)}{\partial x_i}
$$

Итерационный процесс организован следующим образом:

$$
x^{n+1} = x^n + \Delta x
$$

Подробнее см. [2], [3] и [4].

#### Предварительная фильтрация

Базовый алгоритм предварительной фильтрации состоит в усреднении данных за выбранный период времени (окно):

$$
w_k = \frac{1}{N}\sum_{i = t_k}^{t_{k+1}}e_i
$$

### Инфраструктура и вспомогательные компоненты

#### Стратегия параллелизации

Хотя алгоритм Гаусса-Ньютона не допускает параллельного выполнения (или, по крайней мере, затраты распределённой работы перевешивают потенциальные преимущества), параллельный (и распределённый) режим работы вполне естественен для предварительной обработки входных потоков.

Предположим, минимизация выполняется по измерениям с 8 камер (по 2 оси на каждой). В этом случае вход алгоритма состоит из 16 несинхронизированных потоков. С помощью Apache Flink ([5]) каждый поток можно разбить на общие временные окна, а над каждым окном выполнить операцию агрегации, получая статистические характеристики за этот период. Новые потоки (теперь синхронизированные по времени) объединяются в один и подаются на вход алгоритма.

#### Обработка ошибок

Ошибки времени выполнения доставляются в отдельный канал и сериализуются согласно предопределённой схеме. Мониторинг ошибок и их визуализация осуществляются теми же инструментами, что и для корректных результатов выполнения.

## Производительность и масштабируемость

Стратегия параллелизации позволяет масштабировать алгоритм только путём увеличения количества вычислительных слотов для предварительной фильтрации входных каналов, что означает ограничение только их количеством. Однако в настоящее время процесс фильтрации (определение статистических характеристик за определённый период) внутри модуля не является вычислительно сложным и не требует значительного процессорного времени.

## Приложение А. Сравнительный анализ вычислительных систем

### Требования

Функциональные требования:

1. Поддержка режима обработки по времени события;
2. Поддержка работы с временными окнами;
3. Возможности для реализации алгоритмов на нескольких источниках (объединение, группировка и т. д.).

Критерии сравнения:

1. Режим работы — возможности системы для пакетной и потоковой обработки, возможности обработки по времени события и её поведение в случае задержек.
2. Алгоритмические возможности — возможности для реализации алгоритмов на нескольких источниках, поддержка нескольких выходных потоков. Уровень поддержки CEP (Complex Event Processing).
3. Пропускная способность — приблизительная оценка поддерживаемого уровня нагрузки без учёта используемого оборудования.
4. Латентность — приблизительная оценка возможного уровня латентности и её роста при увеличении нагрузки.
5. Эксплуатационные затраты — общая оценка сложности эксплуатации и её роста при увеличении общего числа разработанных алгоритмов. Основана на опыте работы в малых и средних научных лабораториях и производственных командах.
6. Пользовательский опыт — опыт взаимодействия как с точки зрения разработчика, так и с точки зрения конечного пользователя (в небольшой научной лаборатории эти роли часто совпадают). Возможности для реализации алгоритмов на различных языках программирования (Java, Python) или SQL. Наличие специализированных библиотек обработки данных. Наличие графического интерфейса администрирования. Возможность визуального программирования. Общие возможности прототипирования. Уровень поддержки и документации.

Следует отметить, что оценка количественных характеристик не должна восприниматься как факт. Производительность каждой системы сильно зависит от среды, в которой она эксплуатируется. Таким образом, при определённой конфигурации результат может быть прямо противоположным приведённому в таблице выше.

На основании полученных результатов предлагается следующая конфигурация:

1. Apache NiFi используется исключительно как ETL-платформа. Его инструменты обеспечивают сбор информации из широкого спектра разнородных источников (как следствие слабой инфраструктуры) и семантику Replay повторного эксперимента.
2. Apache Flink используется как платформа обработки данных. На начальном этапе предлагается работать в Application mode для устранения необходимости поддержания отдельного кластера. Эксплуатационное преимущество перед Kafka Streams будет достигнуто при расширении алгоритмической базы (как количественно, так и качественно).
3. Инструменты управления задачами Flink должны быть интегрированы в NiFi для сокращения количества поддерживаемых систем. Инструменты визуального программирования, такие как Nussknacker и Ververica, считаются избыточными: отклонение возникающих задач от шаблона приводит к необходимости разработки отдельного узла для каждой задачи, что сводит на нет преимущества систем визуальной разработки.
